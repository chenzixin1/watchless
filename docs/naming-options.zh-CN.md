# 完整视频理解 Skill 命名方案

> [简体中文](naming-options.zh-CN.md) | [English](naming-options.md)

> 最终选择：**Watchless**（Skill 与 GitHub slug：`watchless`）

## 产品机会

这不是会议笔记工具，也不是视频摘要器。它是一条完整的视频理解流水线：从视频下载、词级转录、内容路径判断、语义切分、关键帧选择、说话人识别，到 Light-plus 文本、视觉解说、HTML、PDF、ZIP 和质量审计。

核心用户价值是：

> 把一段必须按时间观看的视频，转换成一份可以按图文顺序完整阅读、检索和分享的视觉文档。

因此名称应满足以下条件：

- 不使用 `session`：产品不限于会议、课程或演讲。
- 不使用 `summary`：输出强调完整理解，不是压缩摘要。
- 尽量不使用 `notes`：容易让人误解为简短笔记或会议纪要。
- 能覆盖 PPT、科普、访谈、播客和产品演示。
- 适合作为 Codex Skill 名、GitHub 仓库名和未来独立品牌名。
- 英文名应容易读、容易拼写，并能形成简洁的 kebab-case slug。

## 三个视角的候选名称

### 产品经理视角：先表达核心价值

| 名称 | 仓库名 | 产品含义 | 优点 | 风险 |
| --- | --- | --- | --- | --- |
| **VideoCodex** | `video-codex` | 把视频编成一份完整、结构化、可阅读的“典籍” | 同时呼应视频文档和 Codex 运行环境，覆盖端到端能力 | 与 Codex 绑定较深，未来脱离 Codex 时需要解释 |
| **Watchless** | `watchless` | 不必看完整视频，也能获得完整理解 | 价值主张非常直接，记忆点强 | 名称是负向表达，不能直接说明图文产物 |
| **VideoAtlas** | `video-atlas` | 把整段视频整理成可导航的内容地图 | 强调完整性、结构和浏览体验 | `Atlas` 更像索引，弱化文字整理能力 |
| **FullScene** | `full-scene` | 不遗漏地保留每个完整语义场景 | 强调完整覆盖和语义切分 | 品牌感一般，容易被理解为视频编辑工具 |
| **ReadTheVideo** | `read-the-video` | 让视频可以像文章一样阅读 | 用户价值清晰，适合传播 | 名称偏长，作为 Skill 和命令略显口语化 |

### 产品设计视角：强调“图 + 文”的体验

| 名称 | 仓库名 | 产品含义 | 优点 | 风险 |
| --- | --- | --- | --- | --- |
| **SceneScribe** | `scene-scribe` | 为每个语义场景选择画面并忠实述写 | 准确描述“场景切分 + 写作”，声音优雅 | 对下载、ASR 和审计等完整流水线表达较弱 |
| **FrameAtlas** | `frame-atlas` | 用关键帧构成整段视频的视觉图谱 | 与“一张图、一段文字”高度一致 | 容易被误解为只做抽帧或图片浏览 |
| **StoryLens** | `story-lens` | 透过镜头重新阅读视频叙事 | 有视觉感和品牌感 | 对 PPT、技术 Demo 等非故事内容不够准确 |
| **ScenePaper** | `scene-paper` | 把视频场景排成一份可以阅读的文档 | 直接表现最终产物 | 名称稍显静态，技术感不足 |
| **FrameTrail** | `frame-trail` | 沿关键帧和文字轨迹浏览完整视频 | 适合时间线式阅读体验 | 没有突出转录和完整语义理解 |

### 软件工程视角：强调流水线和可扩展性

| 名称 | 仓库名 | 产品含义 | 优点 | 风险 |
| --- | --- | --- | --- | --- |
| **FrameForge** | `frame-forge` | 把原始视频“锻造”为关键帧和知识资产 | 工程感强，适合完整流水线 | `Frame` 仍可能让人以为核心只是图片处理 |
| **VideoWeave** | `video-weave` | 把转录、场景、人物和画面编织成文档 | 准确体现多模态合并 | 名称相对温和，记忆点不如 VideoCodex |
| **SceneGraph** | `scene-graph` | 用结构化场景描述整段视频 | 很符合内部数据模型和未来 API | 已是成熟计算机视觉术语，容易产生歧义 |
| **VidCompile** | `vid-compile` | 把视频“编译”为 HTML、PDF 和 ZIP | 技术感强，表达输入到产物的转换 | 面向非工程用户时理解成本较高 |
| **ChronicleKit** | `chronicle-kit` | 将时间线内容整理成可保存的完整记录 | 适合未来扩展为工具集 | 没有明确指出输入是视频 |

## 优先级最高的五个名称

评分维度：核心价值表达 35%、记忆度 25%、Skill/GitHub 可用性 20%、未来扩展性 20%。分数是当前产品定位下的相对判断，不代表域名、商标或 GitHub 名称可用性已经验证。

| 排名 | 名称 | 综合判断 | 关键假设 |
| --- | --- | --- | --- |
| 1 | **VideoCodex** | 最能代表“完整视频被编成结构化图文典籍”，而且天然说明它是 Codex 内的完整 Skill | 用户能理解 `Codex` 的双关，不会只把它当成 OpenAI 官方产品 |
| 2 | **SceneScribe** | 最准确描述核心交互：语义场景、关键帧、忠实述写 | 用户更在意内容生成体验，而不是端到端流水线能力 |
| 3 | **FrameAtlas** | 视觉感最强，与最终图文阅读形态一致 | 产品未来仍以截图型文档为主，不转向纯音频或纯文本处理 |
| 4 | **Watchless** | 最强的用户收益表达，适合传播和产品首页标题 | 用户接受“无需观看”这种略带挑战性的品牌语气 |
| 5 | **VideoWeave** | 最能解释转录、视觉、人物和语义的多模态融合 | 用户愿意通过副标题进一步理解产品，而不是要求名称自解释 |

## 最终方案

### Watchless

正式产品名：

```text
Display name: Watchless
Skill name: watchless
GitHub repository: watchless
Tagline: Watch less. Understand more.
```

推荐副标题：

> Turn any video into a complete visual document, so you can understand it without watching the whole thing.

中文版本：

> 把任何视频变成一份可以完整阅读的图文档案。

推荐一句话介绍：

> Watchless 是一个运行在 Codex 本地的完整视频理解 Skill：从下载和词级转录开始，按内容结构选择处理路径，识别语义场景、关键帧和说话人，最终生成忠实的图文解读、HTML、PDF 和分享 ZIP。

### 为什么不是 Video Notes Maker

`Video Notes Maker` 清楚但缺少品牌识别度，并且 `Notes` 容易让人预期短摘要。`Watchless` 直接表达产品收益：用户不需要完整观看，也能获得完整理解。

1. **结果清晰**：名称直接回答用户为什么要使用这个 Skill。
2. **记忆点强**：比描述型工具名更接近独立产品品牌。
3. **不限制内容类型**：适用于 PPT、科普、访谈、播客和 Demo。
4. **不限制运行平台**：未来即使扩展到 Codex 之外，品牌仍然成立。

## 需要验证的假设

正式改名和上传 GitHub 前，应快速验证：

1. 目标用户看到 `Watchless` 后，是否能从副标题理解它生成的是完整图文文档，而不是更短的视频。
2. GitHub 仓库名、Python 包名、常见域名和社交账号是否存在明显冲突。
3. 用户是否接受“少看视频”这种略带挑战性的品牌语气。
4. 是否需要中文辅助名称；当前建议只使用英文品牌，避免削弱记忆点。

如果用户无法从副标题理解产物形态，首选回退方案是 **SceneScribe**；它仍准确表达“场景 + 图文述写”的核心能力。
